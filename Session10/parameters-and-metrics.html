The parameters

Seven numbers decide the shape of the model. Nothing in the training loop can change them, and every memory and throughput figure further down follows from them arithmetically.

SettingValueWhat it controlsWhat it costs
n_layer6 How many transformer blocks stack on the residual stream. Parameters and time scale linearly. Each block is 1,770,240 weights.
n_embd  D384 The width of the residual stream — how many numbers each token carries. Quadratic. Every weight matrix in a block is D×D or a multiple of it.
n_head6 How many attention heads split that width. Head width is D / n_head = 64. Free. Splitting 384 into 6 heads of 64 costs exactly what one head of 384 costs.
block_size  T256 The longest context the model can attend over, and the length of one training row. Attention work grows with T². Also fixes the learned position table at T×D.
vocab_size  V65 How many distinct tokens exist. Here they are single characters, not BPE pieces. Almost nothing, at 65. This is the number that dominates a real model.
dropout0.0 Fraction of activations randomly zeroed during training. Must be zero here: the gradient check needs the forward pass to be repeatable.
biasFalse Whether linear layers and norms carry an additive bias term. Off, so every count below is pure matrix. Slightly faster and marginally better.

Why nanoGPT prints 10.65M and this page says 10,745,088. Its get_num_params() subtracts the position table by default, giving 10,646,784. Both are correct; they answer different questions. Every FLOP and memory figure on this page uses the full count, because the optimiser holds state for the position table too.
Weight tying. lm_head.weight is transformer.wte.weight returns True. The matrix that reads a token in is the same object that scores it on the way out, so V×D is charged once, not twice. At V = 65 that saves 24,960 weights, which is nothing. At the course's V = 131,072 and D = 4,096 the same trick would save 536.9M — and Session 9 §8 is about why V5 cannot use it.

That last row inverts. Because the vocabulary is 65 characters and the width is 384, the logits here are six times smaller than the hidden states that produced them. The bill Session 9 spends a whole section on simply does not exist at this scale, which is worth knowing before drawing any conclusion from this run about output-head memory.

This is a GPT-2 block, not the V5 block. nanoGPT is pre-norm, like the course's design, but it uses LayerNorm rather than RMSNorm, a learned position table rather than RoPE, and a two-matrix GELU MLP at 4× width rather than a three-matrix SwiGLU. Read the parameter table with that in mind: a SwiGLU block of the same budget would show three MLP tensors at a narrower inner width.

The metrics

Six of them, one per part of the assignment. Each is something the loop does not report on its own — every one had to be instrumented, and four of the six look healthy until they are measured properly.

PART 1

Tensor shapes

Not a measurement so much as a statement of what the loop is holding at each moment. The shape that matters is the last one: logits arrives as [B, T, V] and is flattened to [B·T, V] before the loss.

B and T stop being separate there. 4 sequences of 256 positions become 1,024 independent classification problems, and the loss is their mean. Which is exactly why the question “the mean over what?” has a wrong answer available — that is Part 3.

PART 2

Gradient agreement

7 significant figures

A gradient is the answer to a nudge: move one weight a little, see how far the loss moves, divide. backward() claims to produce that number for every weight at once. This metric checks the claim on one weight, by doing the nudge.

// analytic, what backward() reports
g = w.grad[0,0]

// forward difference — error is O(h)
( L(w+h) − L(w) ) / h

// central difference — error is O(h²)
( L(w+h) − L(w−h) ) / 2h

The two differences are not interchangeable. The forward version is the one the lesson uses to explain what a gradient is, and it is three orders of magnitude worse as a check. Run this in float64. bf16 carries 2.4 decimal digits, so “agree to several decimals” is a bar it cannot clear.

PART 3

Accumulation error

gradient 25% wrong

When a batch is too large to fit, it is run in pieces and the gradients pile up before one optimiser step. The question is how to combine the pieces. Two answers, and they differ only when the pieces hold different numbers of real tokens.

// correct — every token gets one vote
Σ nᵢLᵢ / Σ nᵢ

// naive — every micro-batch gets one vote
Σ Lᵢ / k   (nanoGPT train.py:301)

nanoGPT ships the naive form and is correct to, because it packs fixed-length chunks: every micro-batch holds exactly B·T valid tokens and the two formulas agree to the last digit. Masking a per-micro-batch tail with ignore_index=-1 is what makes them disagree at all.

Read the gradient row, not the loss rows. The loss curves for the two runs sit almost on top of each other. The update does not: on the very first step it points 13° off and is a quarter too long.

PART 4

Gradient norm

warns 14 steps early

The combined length of every gradient in the model, measured before the update. Clipping shrinks everything by one factor when it exceeds a cap, leaving the direction alone and changing only the length.

norm = ‖ ∇ all params ‖₂
if norm > cap: g ← g × cap / norm

// clip_grad_norm_ returns the pre-clip norm.
// train.py:309 calls it and discards it.

Logging that discarded return value costs one variable and is the most useful trace on the dashboard, because it moves before the loss does.

What counts as the loss reacting. A first attempt called any upward move a reaction and found leads whose loss rise was 0.0006 — noise dressed as a finding. Requiring the rise to clear 2σ of the run's own step-to-step noise cut ten findings to two. These runs are also not bit-reproducible despite fixed seeds, so the step indices move between reruns; the lead survives, the numbers 498 and 512 do not.

PART 5

Model FLOPs Utilisation

30.0% of peak

What fraction of the machine the run is genuinely using. A forward and backward pass costs roughly 6N operations per token for a model of N weights, so the numerator is arithmetic. The denominator is where the judgement is.

MFU = 6 · N · tokens/s ÷ peak

// 6 × 10,745,088 = 64.5 MFLOP per token
// peak = 16 SM × 64 × 2 × 2100 MHz

Three denominators, and only one is about this machine. nanoGPT's own estimate_mfu hardcodes an A100's 312 TFLOP/s, which is 73× too large here and reports 0.46%. The theoretical peak above is derived from the device's own SM count and clock, not a datasheet. And a plain 4096³ matmul reaches only 1.47 TFLOP/s on this card — 34% of theoretical — so 34% is the practical ceiling for any fp32 work on it.

What costs the distance to 40%: nothing in the loop. Against what is actually reachable the run sits at 87.6%. Getting further needs different hardware, not better code — and fp16 here measured slower than fp32, so that road is closed too.

PART 6

Precision, and what 0.1 costs

bit-exact against torch

A float divides its bits between three jobs: one sign bit, a few exponent bits that say how big the number is, and the mantissa bits that say which number it is. Exponent bits buy range; mantissa bits buy detail; there is no third source of bits.

value = (1 + M / 2mbits) × 2(E − bias)
bias = 2(ebits−1) − 1

Encoded here by hand — round-half-to-even, subnormals handled — then checked against struct and against torch's own bfloat16 and float8_e4m3fn casts. All three match exactly.

All three keep the same exponent, −4. 0.1 sits nowhere near any format's range limit, so range buys nothing and every bit lost is precision lost. Which is exactly why 0.1 is the wrong number to choose a format with: the failure fp16 has at 10⁻⁸ never shows up here.

Which to train in: bf16 — and not because of anything in that table. On this value alone the table argues for fp32. The row that decides it is the one 0.1 cannot show: bf16 keeps all eight of fp32's exponent bits and reaches down to 9.18e-41, so late-run gradients near 10⁻⁸ survive with no loss-scaling apparatus, while fp16 — more precise at 0.1 — flushes them to zero. Not on this card, though: compute capability 7.5 has no bf16 tensor-core path, which is why every number on this page was produced in fp32.

Every loss on this page is cross-entropy in nats. On its own that number means little, so it is worth carrying two anchors for a 65-token vocabulary.
