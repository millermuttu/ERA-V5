THE TELUGU CODE BUG · te vs tel
A 2-vs-3-char code that passed by luck
# every entry uses the 3-char code… LANG_3_TO_2 = { "asm": "as", "ben": "bn", "guj": "gu", "tel": { "language": "te" } # ← malformed } # pipeline looked up the 2-char code: LANG_3_TO_2.get("te", "te") # → "te" via FALLBACK
The key "te" was never in the table, so .get() returned the default — which happened to equal "te". It "worked" only because the fallback matched by accident. The malformed "tel" entry never resolves.
Source of truth for language
CHOOSE HOW THE LABEL IS ASSIGNED
Every document is labelled by the folder it sits in. The Bengali file inside verified/asm/ is therefore called Assamese, and nothing objects. This is exactly what V4 did.
WHY MISLABELS ARE EXPENSIVE
A Bengali doc counted as Assamese inflates the Assamese token total and starves the Bengali one. Mislabelled docs skew per-language fertility numbers, so every downstream sampling and coverage decision is computed on a corrupted denominator.
THE FIX

Detect at runtime; never trust the provenance path.

The folder tells you where a file came from, not what it contains. Run a language detector on the text, compare it against the claimed code, and quarantine any mismatch before it reaches the tokenizer.
